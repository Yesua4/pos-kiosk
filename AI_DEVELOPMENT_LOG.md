- **Evaluation of the prompt:** the prompt had no requirements, constraints, or expected behaviour of its own; it relied entirely on the exam files in the folder. The output happened to be usable, but the prompt did not control *what* was built. Our later prompts (entries 3–6) are structured.

That is acceptable for a single kiosk, but a store with several kiosks would need a shared database. I tested the cash flow myself in the kiosk (₱45.00 order, ₱200.00 paid, ₱155.00 change) and reviewed the code through the pull requests.

## Entry 3 — M3 · AI-assisted debugging: Enter key completed a payment twice

- **Date:** 2026-10-07
- **Error:** On the Cash screen, M3 clicked **Pay Now** with no amount (the error appears and Pay Now keeps keyboard focus), typed **200** on the keyboard, and pressed **Enter**. The previous transaction was TXN-2026-00001, but this one showed **TXN-2026-00003**, so number 00002 was used up and never shown.
- **Prompt:**
  > Context: Our POS kiosk app in pos-kiosk-repo (vanilla JS). Bug: on the Cash screen, if the Pay Now button has keyboard focus and I press Enter, the payment completes twice and a transaction number is skipped. I got TXN-2026-00003 instead of TXN-2026-00002. Steps: click Pay Now with no amount, type 200 on the keyboard, press Enter. Expected: one payment produces exactly one transaction number. Constraint: don't change the cash validation rules or the touchscreen behaviour. Create branch fix/enter-key-double-payment, find the root cause, fix it, and tell me how to verify.
- **AI response (summary):**
  - **Root cause:** one Enter press ran `payCash()` twice. The `keydown` handler called `payCash()`, and the browser's default action for Enter on a focused button also "clicked" Pay Now, which called `payCash()` again. The cart is cleared only by New Transaction, so the second call also passed validation and created a second transaction.
- **Fix applied** (`js/app.js`):
  ```js
  // before
  else if (event.key === 'Enter') payCash();
  // after
  else if (event.key === 'Enter') {
    event.preventDefault();   // stop the browser's extra click on the focused button
    payCash();
  }
  ```
  plus a guard at the start of `completePayment()`: `if (state.transaction) return;`. An order can only be paid once, which also protects against a fast double tap.
- **Verification:**
  - The same steps after the fix gave **TXN-2026-00004**, and a normal tap-only payment then gave **00005**, so numbers increase by exactly 1.
  - All 15 logic tests pass.
  - Screenshots were taken before (00003) and after (00004, 00005).
- **Evaluation (M3; drafted by Claude at the group's request, confirmed by M3):** Yes, the fix addresses the root cause. The browser's default Enter action "clicked" the focused Pay Now button after our own keydown handler had already paid, and `preventDefault()` stops that second call. The guard in `completePayment()` adds a second layer of protection, which matters on a touchscreen kiosk where a customer might double-tap Pay Now. Limitation: the automated tests cover only the business logic, not keyboard or DOM behaviour, so this fix was verified manually (00003 → 00004 → 00005).
- **Commit / PR:** `b0527f9` / PR #4 (reviewed and approved by Yesua4)

## Entry 4 — M1 · AI-assisted refactoring: explicit formatPeso dependency

- **Date:** 2026-10-07
- **Original code (problem):** `payment.js` used `formatPeso()` without saying where it came from:
  ```js
  // Depends on formatPeso() from format.js (loaded first in index.html).
  'Please enter at least ' + formatPeso(totalCents) + ...
  ```
  Used on its own, `payment.js` crashed with `ReferenceError: formatPeso is not defined`. The tests needed a workaround: `globalThis.formatPeso = formatPeso;`
- **Prompt:**
  > Context: pos-kiosk-repo, js/payment.js. Problem: payment.js uses formatPeso as a hidden global from format.js, so tests/logic.test.js has to set globalThis.formatPeso before requiring it. Goal: make this dependency explicit. Constraint: the app's behaviour and all 15 tests must stay the same. Create branch refactor/payment-formatting, show me the original code and the improved code, and verify with the tests before and after.
- **Improved code:**
  ```js
  const formatAmount = typeof require === 'function' ? require('./format.js').formatPeso : formatPeso;
  'Please enter at least ' + formatAmount(totalCents) + ...
  ```
  The `globalThis` workaround was removed from the tests. The local name is `formatAmount` because all browser scripts share one global scope, and declaring `formatPeso` a second time would crash the page with "Identifier 'formatPeso' has already been declared".
- **Behaviour verification:**

  | Check | Before | After |
  |---|---|---|
  | Logic tests | 15 passed | 15 passed |
  | `payment.js` on its own | ReferenceError | Works ("short by ₱40.00") |
  | App (₱20 for ₱45; ₱200 for ₱45) | Rejected; ₱155.00 change | Same |

- **Evaluation (M1; drafted by Claude at the group's request, confirmed by M1):** The explicit dependency is better because `payment.js` now states where `formatPeso` comes from. It no longer crashes when used on its own, and the tests no longer need a hidden workaround. Behaviour did not change: 15/15 tests passed before and after, and the app showed the same messages. Limitation: the `typeof require` check is still a workaround for not using JavaScript modules. With ES modules or a build tool, a normal `import` would be cleaner, but that would add setup that this simple project does not need.
- **Commit / PR:** `675183f` / PR #5 (reviewed and approved by chuialnaj-cyber)
